# House style for software product blogs

Read once for software-product outlines, drafts, edits or a requested style review.
Skip setup, source intake and voice learning. Stay within the requested edit scope.

## Defaults, with author control

Current instructions and selected team/author preferences override these defaults.
Preserve imported dialect, deliberate phrasing, approved structure and exact code.
Resolve conflicts through [existing scope rules](../hub/memory.md). Retain article
pins; a new guide revision never silently changes an active article.

- **Reader:** establish their concrete problem and the post's useful takeaway
  early. Reuse the brief; avoid a generic industry preamble.
- **Voice:** be a helpful, informed colleague. Keep precise technical terms and
  explain unfamiliar ones. Prefer direct verbs. Remove empty praise and needless
  difficulty judgments such as “just configure.” Preserve personality and rhythm.
- **Mechanics:** for new prose without a preference, use US English, sentence-case
  headings and ordinary contractions. Use consistent terminology and descriptive
  links. Retain official names; format literal identifiers/commands as code.
- **Value:** explain how a capability changes the reader's work and its relevant
  limits. A plausible mechanism does not prove a measured or customer benefit.
- **Shape:** give each section a job. Use prose for reasoning, lists for steps or
  parallel items, tables for comparisons. No compulsory FAQ, CTA or word count.

Illustrative repair, only if supported: “Seamlessly simplify setup” → “The installer
checks required tools before opening sign-in.” Do not invent that behavior.

| Need | Read |
| --- | --- |

| Describe features, availability or tradeoffs | [Software claims](software.md) |

Reuse unchanged references. A polish flags visible evidence gaps without starting
research. Requested style findings use existing `proofread`, with passages/rules
inspected; claim verification stays in [fact check](../modules/blog-fact-check.md).
Neither style feedback nor untested examples establish factual correctness.
