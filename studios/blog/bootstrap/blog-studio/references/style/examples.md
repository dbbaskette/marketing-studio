# Practical examples and procedures

Use only when the post includes runnable steps, code or configuration. Match the
reader's experience: a learning exercise needs more guidance than a focused task.

1. Identify the relevant environment, versions, prerequisite state, dependencies
   and privileges. Show required inputs and distinguish example values from secrets.
2. Introduce each sample's purpose. Use a fenced block with the correct language;
   distinguish commands, configuration and expected output. Mark omissions with
   a language-appropriate comment and describe the snippet as incomplete.
3. Explain consequential flags or design choices near the sample. Avoid a wall of
   code followed by a paraphrase of every line. Link a verified complete example
   when it materially helps; no invented repository links or screenshots.
4. Include an observable result check and a likely failure/recovery path. For an
   exercise that creates resources, include relevant cleanup and cost context.
   Scope destructive examples explicitly and use disposable names/data.
5. State actual verification: executed with the named environment, reviewed only,
   or illustrative/pseudocode. Successful reasoning about code is not a test run.

Correct grammar does not authorize changing command syntax, placeholders or API
names. Do not remove error handling just to shorten an example without explaining
its instructional scope. Testing code that needs accounts, paid resources or
external mutations follows existing authorization; writing a tutorial does not
itself authorize those actions. If execution is unavailable, retain the article
and identify the untested portion rather than claiming reproducibility.

For changed setup details, use permitted primary documentation. Maintain sources
and any available test evidence through existing source/note storage.
Basis: Google's code-sample guidance and Diátaxis; [source map](sources.md).
